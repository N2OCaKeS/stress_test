# Нагрузочное тестирование astraeventsd

Скрипт для измерения производительности регистрации событий через демон
`astraeventsd`

## Метрики

- **Время обработки вызова регистрации на клиенте** — интервалы между
  последовательными подтверждениями `successfully registered` в stdout
  генератора и достигнутая пропускная способность.
- **Время до стабилизации журнала** — от старта прогона до момента, когда
  файл журнала `astraeventsd` перестаёт расти.
- **Утилизация CPU и RSS процесса `astraeventsd`** во время прогона.
- **Потери сообщений** — сравнение числа подтверждённых регистраций и
  числа реально появившихся записей в журнале.

Объёмы нагрузки по умолчанию — 1000 / 10 000 / 50 000 / 100 000 / 150 000

## Запуск

```bash
./astraeventsd_load_test.py \
    --generator-bin ./event-generator \
    --volumes 1000,10000,50000,100000,150000 \
    --events server_started,server_stopped,printer_added \
    --label baseline \
    --out-dir results/baseline
```

### Параметры CLI

| Флаг | По умолчанию | Назначение |
|---|---|---|
| `--generator-bin` | `./event-generator` | путь к бинарю `event-generator`/`astra-event-register` |
| `--transport` | `astraeventsd` | `astraeventsd` или `syslog-ng` |
| `--events` | `server_started` | список ID событий через запятую (должны быть из `event-generator -l`) |
| `--volumes` | `1000,10000,50000,100000,150000` | список объёмов регистрации через запятую |
| `--repeats` | `1` | число повторов на каждый объём |
| `--delay-ms` | `0` | пауза между вызовами генератора, мс |
| `--rate` | — | альтернатива `--delay-ms`: целевая частота событий/сек (взаимоисключающе с `--delay-ms`) |
| `--journal` | автоопределение из `/etc/astraeventsd/config.yaml` | путь к файлу журнала `astraeventsd` |
| `--service` | `astraeventsd` | имя systemd-юнита демона (для поиска PID) |
| `--daemon-pid` | — | PID демона напрямую, если не через systemd |
| `--label` | `baseline` | метка сценария (`baseline`/`mrd`/...) — попадает в имя серии и в отчёт |
| `--out-dir` | `results` | куда сохранять сырые json-результаты (`report.json`) |
| `--stabilize-quiet` | `1.0` | сколько секунд журнал должен не расти, чтобы считать его стабилизировавшимся |
| `--stabilize-timeout` | `60.0` | максимальное время ожидания стабилизации журнала, с |
| `--poll-interval` | `0.2` | интервал опроса журнала, с |
| `--sample-interval` | `0.2` | интервал сэмплирования CPU/RSS демона, с |
| `--cooldown` | `1.0` | пауза между прогонами, с |

## Стенд

- Ресурсы фиксированы по двум профилям:
  - testvm1 (низкие ресурсы) — 2 vCPU / 4 ГБ RAM
  - testvm2 (верхние ресурсы) — 16 vCPU / 16 ГБ RAM

## Результат

Скрипт печатает ход выполнения в stderr (объём, число повторов, throughput,
потери, стабилизация, CPU) и сохраняет сырые результаты серии в
`<out-dir>/report.json`: по одному объекту на каждый прогон (объём × повтор) с
полями по всем метрикам из раздела «Метрики» — подтверждённые/потерянные
события, пропускная способность, статистика интервалов между вызовами
(mean/median/min/max/p95/p99), время стабилизации журнала, CPU/RSS демона.

## Проведение тестирования и обработка результатов

Тестирование проводится в автоматическом режиме с помощью оркестратора ALLTA.

- [ALLTA](https://life.astralinux.ru/pages/viewpage.action?pageId=253888776&src=contextnavpagetreemode)

Сырые json-результаты (`report.json`) забираются с каждой ВМ, сравниваются с
референсными значениями эталонного прогона (throughput, время стабилизации)
через `MathModel(type="ratio")` с расчётом `total_rating`.
