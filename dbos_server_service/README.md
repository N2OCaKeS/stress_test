# DBOS Server Manager

## О проекте

`DBOS Server Manager` — это платформа для централизованного управления тестовыми и инфраструктурными серверами, доступами, конфигурацией и аудитом действий. Проект рассчитан на развёртывание в Kubernetes и состоит из нескольких независимых сервисов.

Основная идея:

- каждый бизнес-сервис разворачивается как отдельное приложение в Kubernetes;
- у каждого сервиса есть собственная база данных PostgreSQL;
- база каждого сервиса работает в отказоустойчивой конфигурации из 2 экземпляров;
- API каждого сервиса запускается минимум в 2 репликах для распределения нагрузки и повышения доступности;
- доступ к данным и операциям ограничивается по отделам и ролям.

## Целевая архитектура

На текущий момент в проекте выделены 7 компонентов:

- `auth_service` — единая точка аутентификации и авторизации;
- `logging_service` — централизованный аудит действий;
- `server_service` — операции по управлению серверами (REST-фасад);
- `server_worker` — фоновый исполнитель hardware-задач (Redfish / ipmitool / SSH);
- `config_service` — хранение и выдача секретов и служебных учётных данных (отложен);
- `web_settings` — web-интерфейс для администрирования платформы (отложен);
- `cli` — кроссплатформенный CLI-клиент для работы с сервисами из консоли (отложен).

Состояние реализации: 4 backend-сервиса production-ready (`auth_service`, `logging_service`, `server_service`, `server_worker`), 4022 проходящих теста (943 + 777 + 816 + 1486), открытых критичных задач нет. Подробности — `STATUS.md`.

Типовая схема развёртывания одного сервиса:

1. В Kubernetes запускаются 2 реплики API.
2. Перед API стоит `Service` или `Ingress`, распределяющий трафик.
3. Данные сервиса хранятся в отдельном PostgreSQL-кластере.
4. PostgreSQL-кластер состоит минимум из 2 экземпляров для отказоустойчивости.
5. Сервисы взаимодействуют друг с другом по внешнему API.

## Общие принципы

### Изоляция по сервисам

У каждого сервиса своя зона ответственности и своя база данных. Это упрощает масштабирование, обновления и разграничение доступа.

Отдельно от backend-сервисов в проект входят клиентские компоненты:

- `web_settings` — административный web-интерфейс;
- `cli` — консольный клиент.

Они не являются самостоятельными доменами хранения данных, а работают как точки входа в уже существующие backend API.

### Изоляция по отделам

Почти все пользовательские действия привязаны к отделу. Пользователь должен видеть только те сущности, которые относятся к его отделу, если у него нет глобальной административной роли.

Модель доступа строится так:

- сначала определяется отдел пользователя;
- к отделу привязан список доступных сервисов;
- внутри каждого сервиса для пользователя действует отдельный набор прав этого сервиса.

### Ролевая модель доступа

Базовая модель ролей для прикладных сервисов фиксированная:

- `guest` — только просмотр документации;
- `reader` — доступ только на чтение в пределах разрешённого отдела;
- `operator` — может читать и изменять данные сервиса в пределах своей зоны доступа, но не управляет ролями;
- `admin` — полный доступ к функциям конкретного сервиса.

Для `auth_service` используется отдельная модель ролей:

- `account_admin` — управляет аккаунтами во всех отделах, но не имеет прикладных прав в других сервисах;
- `department_admin` — создаёт и управляет пользователями только своего отдела.

Все роли назначаются и изменяются только через `auth_service`. Прикладные сервисы не меняют роли пользователей, а только используют уже назначенные права.

После назначения базовых ролей через `auth_service` администратор конкретного сервиса может донастраивать матрицу доступа для своего сервиса и своего отдела: отдельно определять, какие роли могут читать и изменять конкретные сущности. Удаление сущностей остаётся только у `admin`. Сами роли и их назначение пользователям фиксируются через `auth_service`.

Эта модель одинаково применяется ко всем прикладным сервисам: `config_service`, `logging_service` и `server_service`. Клиентские компоненты `web_settings` и `cli` используют ту же модель доступа через `auth_service`, но сами не являются источником ролей.

Отдельное жёсткое правило:

- только `account_admin` может создавать новые сервисы платформы;
- только `account_admin` может удалять сервисы платформы;
- только `account_admin` может выдавать отделу доступ к сервису;
- если у отдела нет доступа к сервису, пользователи этого отдела не могут получать роли этого сервиса и не могут взаимодействовать с его API.

### Аудит

Практически все значимые действия должны попадать в `logging_service`: кто выполнил действие, где, когда, над каким объектом, было ли разрешение и чем завершилась операция.

В аудит должны попадать в том числе:

- входы и неуспешные попытки входа;
- смена пароля пользователем;
- запросы к защищённым endpoint;
- операции чтения и изменения данных;
- административные действия.

Проверки `health` можно не логировать, но весь остальной трафик и действия должны фиксироваться.

## Отказоустойчивость

Базовые требования к отказоустойчивости:

- не менее 2 API-реплик на сервис;
- не менее 2 экземпляров PostgreSQL на сервис;
- readiness/liveness probes для контейнеров;
- централизованные health-check endpoints;
- возможность горизонтального масштабирования API без изменения бизнес-логики.

Примечание: в документации под PostgreSQL-кластером подразумевается отказоустойчивая конфигурация из двух экземпляров. Конкретная реализация может быть выбрана отдельно, например `Patroni`, `Stolon`, `CrunchyData`, `CloudNativePG` или другой оператор.

## Границы ответственности сервисов

### `auth_service`

Отвечает за пользователей, роли, API-токены, OAuth2 и доверенную аутентификацию других сервисов.

Отдельное направление развития сервиса — выделение ботов и сервисных учёток в самостоятельную модель доступа.

### `config_service`

Отвечает за безопасное хранение и выдачу секретов, токенов, служебных логинов и паролей.

### `logging_service`

Отвечает за неизменяемый аудит действий и расследование инцидентов.

### `server_service`

Отвечает за жизненный цикл серверов, операции управления и интеграцию с низкоуровневыми интерфейсами вроде `iDRAC`, `iLO` и SSH-управления хостом.

Сам сервис — это REST-фасад: хранит модели серверов/IPMI/аккаунтов/каталоги, шифрует пароли (AES-256-GCM с версионированием ключа), валидирует action-based права и **диспетчеризует hardware-операции в `server_worker`** через taskiq+Redis. Прямого общения с BMC у `server_service` нет.

### `server_worker`

Фоновый исполнитель задач, делегированных `server_service`. Не имеет HTTP-API. Стек: `taskiq` + Redis broker, своя БД `dev_server_worker` (`tasks`, `audit_outbox`, `worker_heartbeats`).

Содержит 3 hardware-клиента в `clients/`:

- **Redfish** (iDRAC/iLO),
- **ipmitool** (fallback для legacy BMC: Supermicro X9/X10),
- **SSH** (`asyncssh` для `inventory.sync` и `chpasswd`).

Выбор между Redfish и ipmitool делает dispatcher `get_bmc_client` через HEAD `/redfish/v1/` probe; ошибки маппятся на унифицированные коды `BMC_UNREACHABLE` / `BMC_AUTH_FAILED` / `BMC_REJECTED` / `BMC_TIMEOUT` / `BMC_ERROR`.

Аудит в `logging_service` идёт через durable outbox (`FOR UPDATE SKIP LOCKED`, at-least-once, circuit breaker, DLQ при `attempts >= 50`). Периодические задачи: heartbeat, sweep orphaned, retention для `tasks` и `audit_outbox`, lazy re-encrypt секретов.

### `web_settings`

Отвечает за удобный web-интерфейс администрирования, визуализацию прав, работу с объектами системы и доступ к функциям backend-сервисов через GUI.

### `cli`

Отвечает за кроссплатформенный консольный доступ к backend-сервисам, автоматизациям и пользовательским операциям из терминала.
