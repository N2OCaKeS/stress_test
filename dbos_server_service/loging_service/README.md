## Назначение

`logging_service` — централизованный сервис аудита и логирования действий всех компонентов платформы. Его основная задача — сохранить проверяемую историю операций без хранения самих секретов.

## Какие события должны попадать в аудит

- вход пользователя в систему;
- неуспешная и успешная аутентификация;
- неавторизованный запрос к endpoint;
- смена пароля пользователем;
- запрос доступа к секрету;
- операции с сервером;
- изменение ролей и прав;
- системные ошибки и отказы;
- межсервисные вызовы, влияющие на безопасность или состояние данных.

Практически все действия должны попадать в аудит. Исключение можно сделать только для `health`-проверок. Даже простые пользовательские операции без изменения данных, кроме `health`, должны логироваться.

В логирование должны попадать и неавторизованные запросы, например обычный `curl` к защищённому endpoint, если это не `health`.

## Состав записи аудита

Минимальный набор полей:

- дата и время;
- кто выполнил действие;
- в каком сервисе произошло событие;
- над каким объектом выполнялась операция;
- тип действия;
- было ли действие разрешено;
- успешность выполнения;
- технические детали для расследования.

Важно: сервис не должен сохранять значения секретов, пароли и чувствительные данные в открытом виде.

## Модель доступа

Базовый подход:

- пользователи видят логи только своего отдела;
- администраторы отдела видят полный аудит своего отдела;
- глобальный администратор безопасности может анализировать события по всем отделам;
- изменение записей аудита запрещено.

Логи должны быть доступны только на чтение. Допускается отдельная административная настройка срока хранения, ротации и архивирования.

Базовые роли для сервиса фиксированные:

- `guest` — только просмотр документации;
- `reader` — чтение разрешённых логов своего отдела;
- `operator` — чтение логов и изменение служебных настроек логирования, если это разрешено политикой сервиса;
- `admin` — полное администрирование сервиса.

Важно:

- сами роли пользователей меняются только в `auth_service`;
- администратор `logging_service` не создаёт новые базовые роли, а донастраивает матрицу доступа внутри сервиса и внутри своего отдела;
- для сущностей и настроек сервиса отдельно задаётся, какие роли могут их читать и какие роли могут их изменять;
- удаление сущностей и настроек остаётся только у `admin`.

## Логика работы

Каждый сервис после каждого значимого действия отправляет структурированное событие в `logging_service`. Сервис принимает событие, валидирует формат, обогащает его контекстом и записывает в свою базу данных.

Примеры сценариев:

- пользователь попытался войти;
- неавторизованный пользователь сделал запрос к защищённому endpoint;
- пользователь поменял себе пароль;
- пользователь запросил пароль от сервера;
- оператор сменил порядок загрузки через `PXE`;
- сервис отказал в операции из-за недостатка прав.

Взаимодействие с источниками событий выполняется по внешнему API.

## Отказоустойчивость

Для сервиса особенно важны:

- 2 реплики API;
- собственный PostgreSQL-кластер из 2 экземпляров;
- защита от потери событий при временной недоступности одной реплики;
- готовность к дальнейшему добавлению очереди или брокера событий.
