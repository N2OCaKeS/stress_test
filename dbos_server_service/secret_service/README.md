# config_service

## Назначение

`config_service` — сервис безопасного хранения и выдачи секретов, учётных данных и интеграционных токенов. Он нужен для того, чтобы отделы и сервисы получали только те креды, к которым у них есть доступ.

## Общие креды для всех отделов

Помимо отделовых секретов сервис может хранить общие креды, доступные сразу нескольким или всем отделам.

Такие креды нужны для случаев, когда:

- одна интеграция используется всей компанией;
- секрет принадлежит централизованному сервису, а не конкретному отделу;
- одинаковый токен должен выдаваться разным отделам по единым правилам.

Особенности общей зоны:

- общий кред не привязан к одному отделу как владельцу;
- право на чтение общего креда всё равно проверяется в контексте отдела пользователя;
- администратор `config_service` может выдавать право на чтение общего креда только пользователям внутри своего отдела;
- такое право должно зависеть не только от сервисной роли, но и от отдельного разрешения на чтение общего креда;
- глобальный доступ для всех пользователей всех отделов не должен открываться по умолчанию.

## Что хранит сервис

Примеры сущностей:

- токены для `Jira`, `Confluence`, `Git` и других внешних систем;
- логины и пароли внутренних сервисов;
- учётные данные интеграций;
- технические секреты для автоматизации;
- метаданные о владельце секрета, отделе и правилах доступа.

Пример токенов:

- `git` — токен для автоматизаций;
- `jira` — токен для публикации автоматических отчётов.

## Основные задачи

- безопасное хранение секретов;
- выдача секретов по роли и принадлежности к отделу;
- учёт того, что сам сервис может быть полностью недоступен для части отделов;
- разделение секретов по зонам ответственности;
- аудит доступа к секретам;
- ротация и отзыв секретов в будущем.

## Границы ответственности

`config_service` отвечает только за секреты и конфигурационные данные ограниченного доступа.

Сервис не отвечает за:

- аутентификацию пользователей;
- аудит всех действий платформы;
- непосредственное управление серверами.

## Модель доступа

Роли сервиса:

- `reader` — чтение разрешённых секретов в пределах своего отдела;
- `operator` — может читать и изменять креды и связанные данные сервиса, но не управляет ролями;
- `admin` — полное администрирование секретов сервиса;
- `guest` — только просмотр документации.

Важно:

- сами роли пользователей меняются только в `auth_service`;
- в `auth_service` изначально существуют базовые роли `guest`, `reader`, `operator`, `admin`;
- администратор `config_service` не создаёт новые базовые роли, а донастраивает матрицу доступа внутри сервиса и внутри своего отдела;
- администратор `config_service` может отдельно указать, какие роли могут получать конкретный токен и какие роли могут изменять конкретный токен;
- удалять токены и другие сущности `config_service` может только `admin`.

Правило доступа:

Сначала проверяется, доступен ли `config_service` для отдела пользователя. Если сервис не подключён к отделу, доступ запрещается полностью. Если сервис отделу доступен, пользователь может получить только те креды, которые принадлежат его отделу или явно разрешены политикой доступа. Это правило распространяется и на общие креды: даже если секрет общий для всех отделов, пользователь должен иметь явное право на его чтение внутри своего отдела. Глобальный просмотр всех секретов должен быть запрещён по умолчанию.

## Получение токенов

Базовая схема получения токена:

```http
GET /api/config/v1/tokens/
Content-Type: application/json

{
  "token_name": "<имя_токена>"
}
```

Если у пользователя или бота есть право на конкретный токен, сервис возвращает значение токена. Если права нет, сервис возвращает `403 Forbidden`.

## Матрица доступа к токенам

Для каждого токена настраиваются как минимум 2 независимых набора прав:

- какие роли могут получить токен;
- какие роли могут изменить токен.

При этом удаление токена не входит в обычную донастройку прав и всегда остаётся доступным только для `admin`.

Для общих кредов матрица доступа дополняется ещё одним уровнем:

- отдел должен иметь доступ к самому `config_service`;
- внутри отдела у пользователя должна быть сервисная роль, которой разрешено чтение конкретного общего креда;
- при необходимости у пользователя должно быть дополнительное право на чтение общих кредов или конкретного общего секрета.

## Пример сценария

Пусть в `config_service` для отдела есть 2 токена:

- `git` — для автоматизаций;
- `jira` — для публикации автоотчётов.

В `auth_service` уже существуют базовые роли `guest`, `reader`, `operator`, `admin`. Администратор `config_service` для своего отдела донастраивает матрицу доступа:

- токен `git` могут получать роли `reader`, `operator`, `admin`;
- токен `git` могут изменять роли `operator`, `admin`;
- токен `jira` могут получать роли `reader`, `operator`, `admin`;
- токен `jira` могут изменять роли `operator`, `admin`;
- удалять токены может только `admin`.

После этого:

- пользователю `git_bot` через `auth_service` назначается такая роль, которая даёт право получить токен `git`;
- пользователю `jira_bot` через `auth_service` назначается роль, у которой нет права на получение токена `git`.

Тогда запрос:

```http
GET /api/config/v1/tokens/

{
  "token_name": "git"
}
```

для `git_bot` завершится успешно и вернёт токен `git`, если его роль входит в список ролей, которым разрешено получение этого токена.

Тот же запрос для `jira_bot` должен вернуть `403 Forbidden`, потому что его роль не входит в список ролей, которым разрешено получение токена `git`.

Пример с общим кредом:

- в сервисе есть общий токен `company_git_mirror`;
- он доступен для чтения не автоматически всем отделам, а только тем, для которых администратор настроил соответствующее правило;
- администратор отдела может разрешить чтение этого токена только сотрудникам своего отдела, у которых есть нужная сервисная роль и отдельное право на чтение общих кредов.

Тогда сотрудник отдела с ролью `reader`, но без специального разрешения на общий кред, должен получить `403 Forbidden`. Сотрудник того же отдела с нужной ролью и дополнительным правом сможет получить `company_git_mirror`.

Если пользователь или бот делает много запрещённых запросов подряд, учётная запись должна блокироваться или временно баниться по политике безопасности.

Для автоматизаций стоит отдельно учитывать сервисные учётные записи и ботов, чтобы в будущем их жизненный цикл можно было отделить от обычных пользовательских аккаунтов.

## Интеграции

- использует `auth_service` для проверки пользователя, отдела и ролей;
- отправляет события доступа в `logging_service`;
- может использоваться `server_service` для получения технических секретов, если это разрешено политикой.

Взаимодействие с другими сервисами выполняется по внешнему API.

## Требования к безопасности

- шифрование секретов при хранении;
- аудит каждого чтения, изменения и попытки доступа к секрету;
- аудит каждого успешного и неуспешного запроса на получение токена;
- маскирование значений в логах и ответах;
- минимизация числа пользователей с административным доступом;
- подготовка к ротации секретов без простоя API;
- защита от перебора токенов и бан учётной записи при большом количестве запрещённых запросов.

## Развёртывание

Целевая схема:

1. 2 реплики API в Kubernetes.
2. Собственный PostgreSQL-кластер из 2 экземпляров.
3. Внутренний доступ через сервисную сеть Kubernetes.
4. Отдельные политики доступа на уровне namespace и сервиса.
