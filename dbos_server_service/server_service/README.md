# server_service

## Назначение

`server_service` — основной прикладной сервис для управления серверами. Через него пользователи получают доступ к действиям над физическими или виртуальными машинами в рамках своей зоны ответственности.

## Основные возможности

- просмотр списка серверов и их статусов;
- определение, кем занят сервер;
- хранение сетевой и системной информации о сервере;
- выдача и смена серверных паролей по правилам доступа;
- перезапуск, включение и выключение серверов;
- управление порядком загрузки;
- работа с `PXE`;
- интеграция с `iDRAC` и `iLO`;
- добавление и удаление пользователей сервера;
- базовая настройка ОС после переустановки;
- привязка локального пользователя сервера к пользователю из `auth_service`.

## Данные о сервере

В сервисе должна храниться информация о сервере, например:

- `IP`-адрес;
- версия и семейство ОС;
- `SSH`-порт;
- связь с таблицей версий ОС;
- список основных пакетов и их версий.

Также нужен endpoint, который обновляет информацию о версии ОС на сервере.

Таблица версий ОС должна обновляться автоматически.

## Пользователи сервера

В базе данных должна быть отдельная таблица связей по пользователям сервера, где хранятся:

- логин;
- пароль;
- наличие прав `sudo`;
- список групп;
- привязка к пользователю из `auth_service`.

## Границы ответственности

`server_service` управляет жизненным циклом серверов и связанными с ними операциями.

Сервис не должен самостоятельно решать:

- кто аутентифицирован;
- кому разрешён доступ к секрету;
- как хранить глобальный аудит.

Для этого он использует:

- `auth_service` — для проверки прав;
- `config_service` — для получения технических секретов;
- `logging_service` — для аудита всех действий.

Взаимодействие с другими сервисами выполняется по внешнему API.

## Модель доступа

Роли сервиса:

- `guest` — только просмотр документации;
- `reader` — просмотр серверов своего отдела без чувствительных данных;
- `operator` — может выполнять разрешённые операционные действия и изменять данные сервиса, но не управляет ролями;
- `admin` — полный контроль над серверами и сущностями сервиса.

Принцип доступа:

Сначала проверяется, доступен ли `server_service` для отдела пользователя. После этого пользователь видит только серверы своего отдела, а чувствительные операции дополнительно проверяются по роли и журналируются.

Важно:

- роли пользователей назначаются только в `auth_service`;
- базовые роли `guest`, `reader`, `operator`, `admin` фиксированы;
- администратор `server_service` не меняет роли пользователей, а настраивает только то, какие операции и данные доступны каждой роли внутри сервиса;
- для каждой сущности можно отдельно определить, какие роли могут её читать и какие роли могут её изменять;
- удалять серверы, серверные учётные записи и другие сущности сервиса может только `admin`.

## Матрица доступа к сущностям

Для сущностей `server_service` права настраиваются отдельно как минимум по двум направлениям:

- какие роли могут читать сущность;
- какие роли могут изменять сущность.

Примеры сущностей:

- карточка сервера;
- учётная запись на сервере;
- сетевые параметры;
- параметры загрузки;
- данные о версиях ОС и пакетов.

Удаление любой сущности не входит в обычную донастройку прав и всегда остаётся доступным только для `admin`.

## Примеры операций повышенного риска

- получение пароля от сервера;
- смена пароля;
- удалённое выключение;
- изменение порядка загрузки;
- запуск переустановки через `PXE`;
- изменение списка пользователей сервера.

Для таких операций желательно предусмотреть:

- обязательный аудит;
- подтверждение полномочий;
- ограничение по ролям;
- трассировку инициатора и результата.

## Развёртывание

Целевая схема:

1. 2 реплики API в Kubernetes.
2. Собственный PostgreSQL-кластер из 2 экземпляров.
3. Интеграции с другими сервисами платформы по внешнему API.
4. Возможность горизонтального масштабирования API-слоя.

## Технологии

- `Python 3.12`
- `FastAPI`
- `PostgreSQL`
- `Docker`
- `Kubernetes`
